# Ember operations

Read before merging to `main`, deploying, adding a static asset type, touching the app shell or service worker, checking the live app, or touching backups, the database container, the Docker daemon, systemd units or slices, or anything else shared with the host. The Production data rules in the root `AGENTS.md` are hard limits on top of this.

| File                                 | Purpose                                                                                                          |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| `auto-deploy.sh`                     | Timer entry point: fast-forwards the account's checkout and runs `deploy.sh` on a green `main`, holding failures |
| `deploy.sh`, `rollback.sh`, `lib.sh` | Fetch and switch a release, roll back to the previous healthy one; `lib.sh` holds the checks                     |
| `backup.sh`, `restore-check.sh`      | Validated `pg_dump` of the live database and a restore drill into a disposable validation database               |
| `install.sh`                         | Installs the user units, slices, the reviewed launcher and alert notifier; restarts nothing                      |
| `start.sh`                           | `ember.service`'s launcher (installed copy): runs the current release's image as the `ember-app` container       |
| `notify.sh`                          | Sends a signed alert to the owner's alert webhook, queueing it while the webhook is unreachable                  |
| `docker.sh`, `docker-host.sh`        | The Docker CLI pointed at Ember's own rootless daemon                                                            |
| `compose.local.yml`                  | The `ember-postgres` container (development daemon, and the live one with `EMBER_PG_PORT`)                       |
| `limited.sh`                         | Runs the npm test scripts in the capped `ember-jobs.slice`                                                       |
| `isolation-check.sh`                 | Shows what the service account can and cannot reach                                                              |
| `image-smoke.sh`                     | Runtime smoke test of a built image with synthetic settings (`docs/ci-and-images.md`)                            |
| `ghcr-retention.sh`                  | Lists, or with `--delete` deletes, old versions of the GHCR image; CI runs it as a dry run                       |
| `host/`                              | Root-run account setup, the egress firewall, the user-manager drop-in and the `ember-run` entry point            |
| `systemd/`                           | The app, Docker daemon, Tailscale device, auto-deploy timer, notifier units and slices                           |
| `test-*.sh`, `test-ember-run.py`     | Synthetic checks of install, launcher, deploy, auto-deploy, release switch and `ember-run`                       |

`test-release-switch.sh` needs a systemd user session and runs only locally; CI runs the other checks (`docs/ci-and-images.md`).

## Releases and deploy

### Release layout

The live app runs from releases, never from a checkout, so source can be edited and built freely. It runs as the `ember` service account (Service account below), so every `~` below is that account's home. The `ember.service` user unit (`ops/systemd/`, installed with `ops/install.sh`) serves `~/.local/share/ember/current`, a symlink to `releases/<commit>/`. A release holds `IMAGE`, one line naming the image CI published for that code by digest (`ghcr.io/eduard-cc/ember@sha256:<digest>`), `REVISION`, and `dist/`, the web shell copied out of that image. `ember.service` runs it as the `ember-app` container in Ember's own Docker daemon, on the database's Compose network, published on `127.0.0.1` only, read-only, without capabilities, with `--init` and its own limits (768 MiB memory, 1.5 CPUs, 256 tasks) inside `ember-live.slice`. The app runs on the image's own Node; the account has none.

`ember.service` starts it through `~/.local/lib/ember/start.sh`, a copy of `ops/start.sh` that `ops/install.sh` installs, so advancing the checkout never changes what the unit runs. It passes the container the variables in `runtime.env` by name, replacing three: the listen address (`0.0.0.0` inside the container), the web root (the image's `/app/web`) and the database URL, whose `127.0.0.1:55438` becomes `ember-postgres:5432` on the Compose network. It refuses a release without `IMAGE`, an `IMAGE` that is not exactly one image by digest, and any other database URL. The daemon never pulls at start: the image is the one `ops/deploy.sh` pulled and checked.

Releases built on the host before images (`dist/` and `server/`, no `IMAGE`) can remain in `history` until they age out; `ember.service` cannot run them, so `ops/rollback.sh` skips them.

Runtime settings and secrets live in `~/.config/ember/runtime.env` (mode 0600, outside the repository). The app has its own tailnet device, `ember`, run by the `ember-tailscale.service` user unit (userspace networking, UDP 41642, state in `~/.local/share/ember-tailscale`); its Tailscale Serve config proxies HTTPS 443 to the service on loopback, so the app has its own origin. `EMBER_ORIGIN` must be that address.

### What `ops/deploy.sh` checks

- It deploys the image CI tested and published for the commit's code, never a build of its own. It reads the `ember-image` artifact of the newest green push run of that code that published an image (a docs-only run publishes none, so a docs-only commit uses its code commit's image; a run whose `Publish image` job succeeded but whose record is gone is refused) with the account's read-only token and refuses unless the record is exactly one line, `ghcr.io/eduard-cc/ember@sha256:<digest> <commit>`, naming that run's own commit. It pulls that digest (no tag is ever resolved on the host) and refuses unless the image's `org.opencontainers.image.revision` label is that commit and its `source` label is this repository. It copies the web shell out of the image into the release's `dist/`, writes `IMAGE`, switches `current` atomically and restarts the unit.
- Before it switches it checks that the installed launcher matches the checkout's `ops/start.sh` and that `ember.service` runs it; after a change to either, run `ops/install.sh` in the account first, or every deploy refuses with "run ops/install.sh".
- After the switch it checks that the serving release owns the port (an `ember-app` container running exactly the image `IMAGE` names, published on `127.0.0.1` only, with the listener being the Docker daemon's `rootlesskit` in `ember-docker.service`), `/api/v1/health` on loopback (waiting up to two minutes for startup migrations) and through Serve, and that Serve returns this release's `index.html`, `sw.js`, `manifest.webmanifest` and every precached file byte for byte. Any failure rolls back automatically and alerts the owner.
- A lock prevents overlapping deploys and rollbacks. `ops/auto-deploy.sh` holds it for its whole run and `ops/deploy.sh` reuses it, so a rollback started meanwhile refuses with "another deploy or rollback is running"; run it again once the timer's run ends. The newest five releases in `history` are kept, with the images they name; any other image of this repository in Ember's daemon is removed by its digest (never a prune). Rollback therefore never needs the registry.
- The server applies migrations on startup. It lists a release's migrations with that release's own code (the image's Node in a container without network). When a release adds migrations, the deploy first runs `ops/backup.sh` into `~/.local/share/ember-backups/`, restores it into a validation database, compares record and migration counts with `ember` and drops the copy; any failure cancels the deploy. Writes between the backup and the restart are not in it. The newest three pre-deploy backups are kept; manual archives there are never rotated.
- `ops/test-release-switch.sh` exercises the switch, health check, launcher and rollback against synthetic releases, a fake `docker` and a throwaway unit; it needs systemd and is local-only. `ops/test-deploy.sh` runs `ops/deploy.sh` and `ops/rollback.sh` against a throwaway git origin, a fake `gh`, `docker` and `curl` with a synthetic registry and database, and stub backups: every refusal, how a failed pull is judged, the backup gate, docs-only commits, automatic rollback, a release built on the host left in history, and image retention.

### Shipping through a PR

- Every change reaches `main` through a PR; the `main` ruleset refuses direct pushes, force pushes and deletion, and requires the `CI` check (`docs/ci-and-images.md`). Work on a short-lived branch, push it and open a PR whose description opens with one or two short sentences on what it changes and why, adds short bullets only when the PR does several separate things, puts anything the reviewer must act on (deploy order, migration, risk) on a line starting with **Note:**, and doesn't restate what CI reports.
- Merge with `gh pr merge <n> --squash --auto --match-head-commit <sha>`, where `<sha>` is the head you verified and had reviewed: GitHub squashes once `CI` passes on that exact head (the repository allows auto-merge and squash merges only) and refuses if the branch moved meanwhile. Merging is shipping.
- If `main` moved after the PR's CI ran, merge `origin/main` into the branch (never force-push a pushed branch) and let CI run on the new head.

### Deploying

- Main deploys itself. `ember-auto-deploy.timer` (installed and started by `ops/install.sh`) runs `ops/auto-deploy.sh` five minutes after each run ends. Once CI has passed for the head of `origin/main`, it fast-forwards `~/src/ember` and runs `ops/deploy.sh` on it. While CI is pending or GitHub is unreachable, it waits for the next run. The account reads GitHub with its own read-only token; if that token stops working, every run with a commit to deploy logs "could not read CI results". Once runs have failed to read GitHub for a day, the owner is alerted once; the first run that reads it again resets that (`~/.local/share/ember/github-unreachable` marks when it began).
- A head commit whose CI fails, whose deploy fails, or which `~/src/ember` cannot fast-forward to (not on `main`) is held in `~/.local/share/ember/auto-deploy.hold`: the owner is alerted once and it is never retried. A commit is held while it deploys too, so a run killed by the unit's 30-minute timeout is not retried (systemd's failure alert reports it); `ops/deploy.sh` exits 69 when GitHub is unreachable, CI is still running, or a pull fails because the registry gives no answer, or answers 408, 429 or 5xx, for the pull token, the manifest or any blob, which the timer retries instead. After a failed pull it requests each part the pull fetches, in order, and judges the first answer that is not a success; it never guesses from the error text, and a request that fails on this host (curl cannot write its output, say) is a failed deploy. A green run without an image record, a malformed record, an image the registry refuses (missing, no access, no manifest for this platform), a pull that fails twice while the registry serves every part (this host's failure, such as a full disk), or wrong labels is a failed deploy: held, with one alert. `ops/rollback.sh` holds main's head, so the timer does not put it straight back, however many rollbacks follow. The next commit on main replaces the hold; to retry a held commit, run `ops/deploy.sh <commit>` by hand as the service account (Service account below). A failed health check alerts twice: once from the rollback, once from the hold.
- Merging is shipping: a merged PR is live within about five minutes after `main`'s push CI passes, plus the image pull. Still check the live app after each change ships.
- `ops/test-auto-deploy.sh` checks those decisions, and the alert route, against a throwaway git origin, a fake `gh`, a fake alert receiver and a stub deploy; it is local-only.
- `ops/deploy.sh <commit>` sources `ops/lib.sh` from the checkout it is run from (the service account's `~/src/ember`); a release never updates those scripts. Fast-forward that checkout first (`git fetch && git merge --ff-only origin/main`, keeping untracked files), or the deploy runs an old health check.
- Never build, install or run dev servers in either `~/src/ember`: the service account's must stay a clean `main` for `ops/deploy.sh`, and the owner's is the base for worktrees.
- The deploy refuses commits not on `origin/main` or whose latest code commit has no successful push CI run (a docs-only commit inherits its code ancestor's run without waiting for its own; cancelled runs don't count).
- A release that adds migrations is preceded by `ops/backup.sh` plus `ops/restore-check.sh`, and a count comparison against `ember`. Migrations are never rolled back, and a release lacking migrations the database already has is refused.
- Undo with `ops/rollback.sh` (previous healthy image release from `~/.local/share/ember/history`, skipping releases built on the host; the image is still local, so it needs no network). With no earlier image release it refuses and changes nothing. Run it as the service account: `sudo /usr/local/sbin/ember-run -- bash -c 'cd ~/src/ember && ops/rollback.sh'`. Roll forward again with `ops/deploy.sh <commit>`, which reuses the kept release while it is what the deploy would make (the image CI recorded, pulled again by the same digest if it has left the daemon). A release in `history` or the live one is never replaced by a different one: such a deploy refuses, so a failed replacement can never cost a rollback target.
- To pause deploys, stop the timer in the account (`ember-run -- systemctl --user stop ember-auto-deploy.timer`) and start it again afterwards; `ops/install.sh` starts it too. For a short manual step, hold the deploy lock on file descriptor 9, as `ops/auto-deploy.sh` does: `ember-run -- bash -c 'exec 9>~/.local/share/ember/deploy.lock && flock -n 9 && cd ~/src/ember && <commands>'`. The timer waits meanwhile, and `ops/deploy.sh` and `ops/rollback.sh` run inside it reuse the lock.

### Static assets and the precache

The production server sends only files allowed by `packages/contracts/src/static-files.ts` (`index.html`, `sw.js`, the public shell files, and `assets/*.{js,css,woff2,webp}`). `apps/web/scripts/pwa-build.ts` imports the same rule and fails the build if the service worker would precache a file the server refuses, and `ops/deploy.sh`'s health check fetches `sw.js`, the manifest and every precached URL through Serve byte for byte, rolling back and naming the file on a mismatch. A single missing file makes the service worker's `cache.addAll` fail, leaving installed apps on the old shell while the API looks healthy. A new asset type means widening that one rule. After deploys that touch the shell, still check that the service worker activates on a phone.

### npm dependencies and Node

The lockfiles pin every npm package, and CI and the image build install them with `npm ci`. The live app runs the Node of its image, which the Dockerfile pins by tag and digest; the service account has no Node of its own. Routine updates, the base image included, come from Dependabot (`docs/ci-and-images.md`). Dependabot alerts report advisories in the lockfiles, including ones with no update to apply yet; one still open a day after it was raised becomes a card on the owner's task board. Fix advisories with in-major updates, never `npm audit fix --force`. Dependabot moves the Dockerfile's Node pin (tag and digest together) without a cooldown, so a Node security release reaches a PR within a day; `apps/web/tests/node-image.test.ts` keeps that pin on the `.nvmrc` major, which CI uses.

## Live checks

- The live origin is `EMBER_ORIGIN` in `~/.config/ember/runtime.env`. It is served by Ember's own tailnet device (`ember-tailscale.service`), so it does not appear in the host's plain `tailscale serve status`.
- Verify a deploy by comparing live `/sw.js` with `~/.local/share/ember/releases/<sha>/dist/sw.js`. Also check that `ember-app` runs the digest in `releases/<sha>/IMAGE` (`ops/docker.sh inspect --format '{{.Image}}' ember-app` against `ops/docker.sh image inspect --format '{{.Id}}' <image>`). The app's own log stays in `journalctl --user -u ember.service`.
- The server gzips responses only for clients that send `Accept-Encoding` (never Range requests). The plain-`curl` health check sends none, so its byte-for-byte comparisons still see the uncompressed files.
- Small images are inlined into the JS bundle by Vite, so a live check must compare hashes of non-inlined assets rather than grep for file names.

### Read-only live offline-shell check

Use a fresh Pixel 6 browser context and intercept only `**/api/**` with a synthetic unavailable response, so owner history and mutations stay off the wire. Avoid a catch-all `context.route('**/*')`, even with `route.continue()`: in Chrome it left the reloaded page without a service-worker controller. Wait for activation, reload under the worker, then test offline reload and reopening in a fresh tab. Never print private page text.

### Crash loops

If the service crash-loops (five starts in five minutes), systemd stops it and `ember-notify-failure@` sends an alert. Its helper is a reviewed copy of `ops/notify.sh` installed at `~/.local/lib/ember/notify.sh` by `ops/install.sh`, never a script executed from the checkout: the owner's retained development daemon uses the same notifier. After a notifier change, reinstall from the reviewed source. User units cannot trigger the root `notify-failure@` unit, so this is a user-level equivalent.

## Backups and restore drills

### Local backups

`ops/backup.sh` writes task-scoped plaintext custom-format PostgreSQL archives (session data excluded) to `~/.local/share/ember-backups/`, which stays on the machine. `ops/restore-check.sh <archive> <db>` restores one into a new isolated validation database only; the row-count comparison with `ember` is left to the caller. Both have a real PostgreSQL test. Preserve archives privately.

### Off-device backup

A nightly root-owned backup job outside this repository dumps the live `ember` database with `pg_dump -Fc` through the service account's Docker socket and stores the dump in an encrypted off-device backup. Keep the `ember-postgres` container, the `ember` database and user, and the daemon socket stable (see Rootless Docker daemon below).

Restore drill: fetch the newest off-device dump read-only (never run `forget`, `prune` or `unlock` on the backup repository by hand), restore it with `ops/restore-check.sh <dump> <db>` as the service account into a new validation database, then compare every table with `ember`: row count and an ordered `md5` of all rows, plus the schema from `pg_dump -s`. Differences must be explained by writes after the snapshot time, typically new sessions or synced records. Unlike `ops/backup.sh` archives, this dump is a full `pg_dump` that includes the `sessions` table, so treat the validation database and the local file as secret: drop the database (`ops/docker.sh exec ember-postgres dropdb -U ember <db>`) and `shred -u` the file promptly. Repeat the drill after database changes. Recovery on a rebuilt machine has not been rehearsed (`apps/web/PRODUCT.md` "Remaining Release Gates").

## Service account and Docker daemon

### Service account

The live app and everything that builds or deploys it run as the dedicated `ember` account, never as the owner: `ember-auto-deploy`, `ember.service`, Ember's Docker daemon and database, and its Tailscale device all live in that account's lingering user manager, and every `~` path in this README means its home. Code from `main` and from npm runs there, so treat the account as untrusted:

- It has no password, no login shell and no supplementary groups (sudo, docker, lxd and adm are each a way out), its home is private, and the owner's home is closed to it.
- Unix permissions do not cover the network: every local user can reach loopback services (browser debugging ports, agent gateways, other databases), this host's own tailnet address and Docker bridge networks. A root nftables table, `ember_egress_<uid>` (`ops/host/egress.nft.in`, loaded by `ember-egress-ember.service`, which the account's `user@<uid>.service` requires, so nothing starts without it), lets the account, and the subordinate uids it can switch to in its own user namespaces, reach only the internet, DNS, its own loopback ports (the app and its database), the owner's alert webhook on loopback (alerts only), HTTPS on its own tailnet device (the deploy checks the app through Serve) and nothing else on the host, LAN or tailnet.
- User-unit sandboxing (`ProtectHome=`, `InaccessiblePaths=`, `IPAddressDeny=` and the like) is silently ignored on hosts that restrict unprivileged user namespaces, and the account controls its own user manager anyway. The root-owned `user@<uid>.service.d/ember-isolation.conf` (`ops/host/user-manager.conf`) instead gives the entire manager an inherited mount namespace: an empty read-only `/run`, the account's own runtime directory, just systemd's boot marker/notification/logging endpoints and DNS configuration files, and private temporary directories. Host Tailscale LocalAPI, system D-Bus, printing and other users' sockets are absent. Other printing sockets and the crontab spool are inaccessible; setup refuses an existing crontab so no scheduled code can escape this manager. The namespace, uid permissions and firewall together enforce the boundary. Rootlesskit children cannot unmount these inherited restrictions.
- GitHub access is a read-only token limited to this repository, stored in the account's own `gh` config (it has no keyring). Alerts (`ops/notify.sh`) are posted to the owner's alert webhook, which forwards them as push notifications. `~/.config/ember/alert-webhook` (mode 0600) holds the webhook URL and its HMAC secret; every post is signed and timestamped. Without that file `ops/notify.sh` sends nothing: it logs the alert and fails. The receiving side passes only the alert texts the ops scripts send and replaces anything else with a fixed notice that Ember sent an unrecognised alert, so a new or reworded alert needs its template allowed there too. While the receiver is unreachable (a restart, for example) alerts wait in `~/.local/state/ember/alert-queue`; `ember-notify-retry.path` starts `ember-notify-retry.service`, which sends them in order every 30 seconds until they are taken and gives up on an alert after 24 hours, failing so its own failure alert reports the loss. An alert the receiver refuses is not retried: `ops/notify.sh` fails and the caller logs it. After a change to `ops/notify.sh` or the units ships, rerun `ops/install.sh` in the account: deploys do not reinstall them.
- Set it up with `ops/host/setup-account.sh` (root) and `ops/host/setup-service-user.sh` (as the account), both run from a reviewed checkout. `ops/isolation-check.sh`, run as the account, shows what it can and cannot reach.

If a root-owned manager drop-in changes, stop that account's manager before rerunning setup, then start it again; setup refuses to change the namespace of an active manager. Run Ember commands in the account's own user manager, for example `sudo /usr/local/sbin/ember-run -- bash -c 'cd ~/src/ember && ops/deploy.sh <commit>'`, `sudo /usr/local/sbin/ember-run -- systemctl --user status ember.service` and `sudo journalctl _UID=$(id -u ember) _SYSTEMD_USER_UNIT=ember-auto-deploy.service`. `ember-run` is a reviewed root-owned copy installed by account setup. It pins the protected manager's mount namespace, enters it while privileged, clears groups/environment and drops to Ember before contacting the local user bus; only the fixed OS tools before that drop run as root. Never use `systemd-run` or `systemctl` with `-M ember@`: its same-uid transport runs outside that namespace and exposes host IPC through `/proc/PID/root`. The isolation check probes these process-root paths too. Never execute app code from the account's home or checkout as the owner or as root: the account can rewrite it.

Accepted exposure: the account can read world-readable files and see other users' process command lines, and code running as it can read and change Ember's data and use the Ember tailnet device's identity, which a tailnet ACL tag limits to inbound connections from the owner's devices.

### Rootless Docker daemon

Ember runs its PostgreSQL container in its own rootless Docker daemon, `ember-docker.service` in the service account, with the socket at `$XDG_RUNTIME_DIR/ember/docker.sock` and data under `~/.local/share/ember-docker`. The live `ember` database is published on 127.0.0.1:55438 (`EMBER_PG_PORT=55438 ops/docker.sh compose -f ops/compose.local.yml up -d --wait`); the server accepts that port for the `ember` database only. Development and test databases stay on the owner's own daemon and container on 55439, which keeps no live data. Nothing using that socket can see other apps' containers. Use `ops/docker.sh` (the Docker CLI pointed at that socket, ignoring any exported `DOCKER_HOST`) for every Ember container command; `ops/backup.sh`, `ops/restore-check.sh`, `ops/deploy.sh` and the backup test use it too. CI points `EMBER_DOCKER_HOST` at its runner's daemon instead.

The nightly off-device backup dumps `ember` through the service account's socket (`$XDG_RUNTIME_DIR/ember/docker.sock` in that account) and skips the daemon's raw data directory, which carries a `CACHEDIR.TAG`. Keep the container, database and socket names in line with that job.

### PostgreSQL version

The image is pinned to an exact minor (`postgres:17.N-bookworm`) in `ops/compose.local.yml`, `ops/backup.sh`, `ops/restore-check.sh`, `ops/image-smoke.sh` and CI; `apps/web/tests/postgres-image.test.ts` keeps them equal. Dependabot opens a PR within a week of a newer 17.x minor; it updates only the compose pin, so its CI fails until the other pins move too, and it carries the `hold` label, so it is never merged as is. Minor updates keep the data directory. Back up and restore-check with the old scripts, push the new pin, then recreate the live container at once, as the service account, with `EMBER_PG_PORT=55438 ops/docker.sh compose -f ops/compose.local.yml up -d --wait` (and the development one with plain `ops/docker.sh compose …`). Until then `ops/backup.sh` and deploys that add migrations refuse, because the pin no longer matches the container. To go back, pin the previous minor and recreate again.

## Resource limits

Installed by `ops/install.sh`, units in `ops/systemd/`:

- `ember-live.slice` holds `ember.service`, the Docker daemon, the PostgreSQL container and the app's `ember-app` container (the daemon's `--cgroup-parent`; the app container has its own 768 MiB, 1.5 CPU and 256-task limits so it cannot crowd the database): at most 2 CPUs, 1.5 GiB memory (throttled from 1 GiB) and 512 MiB swap. The app and daemon run at nice 5 with low best-effort I/O priority.
- `ember-jobs.slice` holds test runs (in the owner's user manager): the web app's npm `test:*` scripts and the API's `test:e2e` start through `ops/limited.sh` (nice 10, low I/O priority), browsers, dev servers and test API processes included. At most 4 CPUs, 4 GiB memory and 1 GiB swap. The API build in `pretest:e2e` runs outside it, and the database work tests cause counts against the live slice, since PostgreSQL runs there. CI runs the commands directly. In the service account's user manager it holds the auto-deploy runs (`ember-auto-deploy.service`); the daemon unpacks a pulled image in `ember-live.slice`.

Other services on the host run in the system slice, so these hard caps, not CPU weights, are what protect them. The I/O priority only takes effect under a priority-aware disk scheduler, and the user manager has no I/O controller; disks without such a scheduler (common for NVMe) leave disk I/O uncapped.
