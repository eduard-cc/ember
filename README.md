# Gym Log

A local-first mobile workout tracker with inspectable history, editable templates, preservation-aware Strong CSV import, and a separate privately hosted API. The name is temporary. The prototype baseline is preserved in local Git history; the current foundation is not yet an approved replacement for Strong.

## Run locally

Requires compatible Node.js/npm, Google Chrome for browser tests, and Gym Log's own rootless Docker daemon (see Host isolation) for the isolated PostgreSQL/API integration checks.

```sh
npm ci --include=dev
npm --prefix server ci --include=dev
npm run dev
```

Open http://127.0.0.1:5188. An ordinary installation starts empty. `/?demo=1` is an explicit **development-only** synthetic demo; production builds ignore it. Do not synchronize demo profiles with personal history.

The local API setup and secure credential requirements are documented in `server/README.md`:

```sh
ops/docker.sh compose -f ops/compose.local.yml up -d --wait
# once: create the gym_log_dev role and database, see server/README.md
npm --prefix server run migration
npm --prefix server run dev
```

Use a separate terminal for the API. Development Vite proxies same-origin `/api/v1` requests to loopback port 5190. Development and tests use the `gym_log_dev` database in `gym-log-local` on loopback port 55439; test databases are created from it. The live app alone uses the `gym_log` database and port 5191, configured outside the repository (see Deploy and rollback); never point development at it. These are local development resources, not production deployment. No usable default owner password exists; provision an owner hash through a secure local workflow before interactive authenticated use. Do not paste credentials into chat or tracked files.

## Implemented Phase 2 UI

The main navigation is **Profile / History / Workout / Exercises**, with Workout selected initially.

- **Profile:** total workouts and recorded sets, workouts this week, a 12-week workouts-per-week chart and Settings. The weekly average excludes the current partial week.
- **History:** searchable, paginated workout history with exact source details, Repeat and Save as template.
- **Workout:** Start empty workout and unlimited editable templates. Template targets are not completed sets. Add exercise opens the full-screen exercise library with search, body-part filters, recent rows and thumbnails. Selecting a row adds it and closes the picker; a new search name can be created after choosing its type. The same picker is used in template editing. An active workout can be minimized to browse any tab and resumed from its named bar, which shows elapsed time and completed/total sets. This does not discard the durable local draft.
- **Exercises:** searchable catalog plus all exact recorded/custom names, body-part filters, recent exercises and thumbnails. Names are not fuzzy-matched or merged. Exercise details have **About / History / Charts / Records** tabs: available instructions, equipment and muscle data; actual session sets; applicable per-session trends with exact-value tables; and eligible records with source-workout links. Exercises with history initially open History; others open About. Custom exercises without catalog content explicitly have no instructions.

Settings contains appearance, Strong CSV import and app updates. There is no manual Sync Now control or user-facing Backup & Recovery panel. Synchronization is automatic and normally silent; ownership/authentication blocks, failed saves and rejected changes still surface when action is needed. Removing those controls does not remove storage recovery functions or server backups.

### Exercise content and licensing

Bundled drawings, instructions and muscle data come from the Everkinetic and wger open datasets. `src/catalog/exercises.json` is generated by `scripts/catalog/generate.py`; bundled WebP images live in `src/catalog/images/`. Each sourced item retains title, author, source URL, license URL and adaptation metadata. Exercise About exposes item-level attribution. Drawings are cropped, resized and recoloured; instructions are converted to plain text. Preserve each item's original license, including attribution and share-alike obligations where applicable; these content licenses are not a blanket license for the app. Coverage varies by exercise, and the app does not imply endorsement by the source projects.

## Saving and synchronization

- **Saved on this device** means the IndexedDB transaction committed. It is not protection against clearing browser storage, uninstalling the PWA, device loss, or physical disk failure.
- An unfinished workout belongs to its starting browser installation. It is **not sent to the server**. A second same-origin tab is read-only until the writer closes and it is reloaded.
- Finishing atomically stores valid explicitly completed sets, creates an immutable pending operation and removes the draft. Write failures retain the draft and report a visible storage error rather than claiming success.
- The private trial connects automatically using the owner's Tailscale identity, without an app password or manual sync setup. Completed history, imported history and templates synchronize while the app is open and connected. An expired session reconnects automatically.
- Offline/pending mutations survive reopening; reconnect retries use the same operation identity so a lost response does not duplicate the server write. Previously trusted installations can continue logging offline. Android does not guarantee uploads while the PWA is closed.
- Successful server synchronization is not off-device disaster recovery. Routine sync status is not shown as a permanent card. Rejected/conflicting operations remain visible and retained in storage; there is no automatic merge UI.
- Valid legacy `gym-log:v1` localStorage data migrates transactionally, retaining original bytes. Malformed or unsupported data blocks writes; explicit reset preserves recovery evidence rather than silently overwriting it.

## Import and privacy

The UI accepts a local Strong CSV with preview and explicit replacement of imported history. Native logged workouts and the draft are preserved. Exact file bytes determine source identity; repeated rows, exercise occurrences, original cells, blank-versus-zero values and wall-time timestamps are retained. Imported and native history have distinct server operation kinds so CSV replacement cannot remove native logged workouts.

A private development input can also be made available explicitly:

```sh
GYM_LOG_CSV=/absolute/path/to/strong-export.csv npm run dev
```

Then use `/?localCsv=1`. This loopback-only development route is not present in production output, and is not service-worker cached. Do not expose the development server publicly or on the tailnet. Private CSVs, `.local/`, ignored credentials, database dumps and personal screenshots must not enter tracked source, `public/`, build artifacts or external services. Only synthetic fixtures belong in tests.

## Offline app shell

Production builds include a manifest, icons and a finite service-worker app-shell cache. After a successful initial online load, the shell can reopen offline and use IndexedDB. API responses, private CSVs, JSON payloads and arbitrary runtime requests are not cached. Updates wait instead of silently refreshing the logger; no native background-sync or Android ongoing-notification guarantee is implied.

## Technical recovery and backups

Versioned JSON recovery functions remain in the storage layer, but export/restore is not exposed in the current UI. They preserve domain documents, original import evidence and a local draft without credentials/session secrets. Diagnostic pending operations are labelled, not replayed as old acknowledgements. A restore validates before writing, requires explicit confirmation to replace occupied local data and rebuilds create-only operations; it does not authorize overwriting newer server revisions. Storage backup/restore unit coverage and dataset-reset recovery integration coverage remain. Removing the manual recovery panel changes neither these safety constraints nor the database backup/restore tools below.

The server restore drill uses task-scoped plaintext custom-format PostgreSQL archives, excludes session data and targets only a new isolated validation database. See `ops/backup.sh`, `ops/restore-check.sh` and their real PostgreSQL test. Preserve archives privately. Archives under `~/.local/share/gym-log-backups/` stay on this disk.

### Off-device backup

A nightly root-owned backup job outside this repository dumps the live `gym_log` database with `pg_dump -Fc` and stores the dump in an encrypted off-device backup. Check that the newest off-device dump restores without touching the live database:

```sh
# Fetch the newest dump read-only with the off-device backup's own tooling (outside this repository).
s=$(mktemp -d) db=gym_log_restore_validation_$(date +%Y%m%d%H%M%S)
<fetch the newest off-device dump> > "$s/gym-log.dump"
ops/restore-check.sh "$s/gym-log.dump" "$db"
# compare "$db" with gym_log (below), then:
ops/docker.sh exec gym-log-local-postgres dropdb -U gym_log "$db"
shred -u "$s/gym-log.dump" && rmdir "$s"
```

`--no-lock` keeps the drill read-only on the repository; never run `forget`, `prune` or `unlock` by hand. Unlike `ops/backup.sh` archives, this dump is a full `pg_dump` that includes the `sessions` table, so treat the validation database and the local file as secret and remove them promptly. Before dropping it, compare every table of the validation database with `gym_log` (row count and an ordered `md5` of all rows, plus the schema from `pg_dump -s`); differences must be explained by writes after the snapshot time, typically new sessions or synced records.

Last verified: snapshot `<latest>` restored, and all six tables, the migration sequence and the schema matched live exactly. Recovery on a rebuilt machine has not been rehearsed.


`npm run lint` and `npm --prefix server run lint` apply ESLint's automatic fixes. Both configs use type-aware `typescript-eslint` and React hooks rules for the web app, `typescript-eslint` recommended for the server; each rule turned off or narrowed carries a one-line reason in the config.

Integration checks create migrated disposable databases and generate synthetic credentials in memory. They refuse occupied test ports rather than reusing or terminating unrelated processes. Test harnesses refuse any admin database other than `gym_log_dev`; the live `gym_log` database is never a fixture target. No private export is needed. Do not run two fixed-port integration harnesses concurrently.

### GitHub Actions CI

`.github/workflows/ci.yml` runs format and lint checks, web/server typechecks and builds, unit tests, server E2E against a disposable PostgreSQL 17.6 service on `127.0.0.1:55439`, and Playwright desktop/mobile E2E. The service starts with a throwaway `gym_log_dev` database; tests create and remove their own migrated databases. All inputs are synthetic, with no host credentials or private exports.

CI uses Linux runners, the Node.js major in `.nvmrc` (matching the live service), SHA-pinned actions, npm and Playwright Chromium caches, and a timeout on every job. Cheap checks share one job because GitHub bills each job per started minute. New commits cancel superseded runs for the same branch/PR, so a cancelled `main` run is not a green one. Pushes run only on `main`; PRs run separately. Markdown-only changes and agent plans skip CI, so run `npm run format:check` locally before pushing docs. Browser reports, screenshots and traces upload only on failure and expire after three days; no build artifacts or container images are published. Local browser tests still use installed Google Chrome; `CI=true` selects Playwright's bundled Chromium and two workers without retries.

The integration (including dataset-reset recovery) and PWA suites stay **local-only** to save Actions minutes. Run them, along with the checks above and independent review, **before every code push**. Run fixed-port suites sequentially. CI does not replace real phone testing or authorize deployment by itself.

The budget is at most 1,000 Gym Log Linux runner-minutes/month, shared within the account's 2,000-minute free allowance. Before pushing, query the account's billing usage API and total month-to-date Actions minutes by repository. At 800 Gym Log minutes or 1,600 account-wide, stop triggering CI, verify locally instead, and mention the budget pause in the Discord report. The target is under 15 aggregate runner-minutes per code push, not just elapsed wall time; use the real job start/completion timestamps to measure it.

Measured: the first `main` run (3 October 2026, cold caches) took 2m50s wall time. Jobs took 44s (checks), 1m21s (server E2E) and 2m45s (Playwright), 4m50s of runner time billed as 6 minutes. That allows roughly 160 code pushes a month within the Gym Log budget.

## Deploy and rollback

The live app runs from built releases, never from a checkout, so source can be edited and built freely. The `gym-log.service` user unit (`ops/systemd/`, installed with `ops/install.sh`) serves `~/.local/share/gym-log/current`, a symlink to `releases/<commit>/`. Runtime settings and secrets live in `~/.config/gym-log/runtime.env` (mode 0600, outside the repository) with `GYM_LOG_WEB_ROOT` set to the absolute path of `~/.local/share/gym-log/current/dist` (systemd does not expand `~`). Tailscale Serve on port 8444 proxies to the service on loopback.

```sh
ops/deploy.sh <commit>   # build, switch, restart, health-check; rolls back on failure
ops/rollback.sh          # switch back to the previous healthy release
```

`ops/deploy.sh` refuses commits that are not on `origin/main` or whose latest code commit lacks a successful push CI run (docs-only commits skip CI, so their nearest code ancestor is checked; cancelled runs do not count). It builds a `git archive` export of the commit, keeping only the web shell and the compiled server with production dependencies, then switches `current` atomically and restarts the unit. It then checks that the unit's own process owns the port, `/api/v1/health` on loopback (waiting up to two minutes for startup migrations) and through Serve, and that Serve returns this release's `index.html`. If any check fails it rolls back automatically and alerts Discord. A lock prevents overlapping deploys and rollbacks. The newest five deployed releases are kept, and `history` records healthy deploys for rollback.

The server applies migrations on startup. If a release adds migrations the live `gym_log` database has not applied, the deploy first takes a backup with `ops/backup.sh` into `~/.local/share/gym-log-backups/`, restores it into a validation database, compares record and migration counts with `gym_log`, and drops the copy; any failure cancels the deploy. Writes between the backup and the restart are not in it. Rollback cannot undo a migration, so the newest three pre-deploy backups are kept; manual archives there are never rotated. A release that lacks migrations the database already has is refused, so old code never runs on a newer schema.

If the service crash-loops (five starts in five minutes), systemd stops it and `gym-log-notify-failure@` sends a Discord alert. User units cannot trigger the root `notify-failure@` unit, so this is a user-level equivalent. `ops/test-release-switch.sh` exercises the switch, health check and rollback against synthetic releases and a throwaway unit; it needs systemd and is local-only.

## Host isolation

Gym Log runs its PostgreSQL container in its own rootless Docker daemon, `gym-log-docker.service`, with the socket at `$XDG_RUNTIME_DIR/gym-log/docker.sock` and data under `~/.local/share/gym-log-docker`. Nothing using that socket can see other daemons' containers. Use `ops/docker.sh` (the Docker CLI pointed at that socket, ignoring any exported `DOCKER_HOST`) for every gym container command; `ops/backup.sh`, `ops/restore-check.sh`, `ops/deploy.sh` and the backup test use it too. CI points `GYM_LOG_DOCKER_HOST` at its runner's daemon instead.

The nightly off-device backup dumps `gym_log` through that socket and skips the daemon's raw data directory, which carries a `CACHEDIR.TAG`. Keep the container, database and socket names stable.

Resource limits (installed by `ops/install.sh`, units in `ops/systemd/`):

- `gym-log-live.slice` holds `gym-log.service`, the Docker daemon and the PostgreSQL container: at most 2 CPUs, 1.5 GiB memory (throttled from 1 GiB) and 512 MiB swap. The app and daemon run at nice 5 with low best-effort I/O priority.
- `gym-log-jobs.slice` holds test runs: the npm `test:*` scripts and `server` `test:e2e` start through `ops/limited.sh` (nice 10, low I/O priority), browsers, dev servers and test API processes included. At most 4 CPUs, 4 GiB memory and 1 GiB swap. The server build in `pretest:e2e` runs outside it, and the database work tests cause counts against the live slice, since PostgreSQL runs there. CI runs the commands directly.

System services sit outside the user manager, so these hard caps, not CPU weights, are what protect them. The I/O priority only takes effect under a priority-aware disk scheduler, and the user manager has no I/O controller; disks without such a scheduler (common for NVMe) leave disk I/O uncapped.

## Mobile logger and analytics

Exercise Charts offers best reps, highest recorded load, session volume and estimated 1RM for weighted work; assisted work offers best reps and least assistance. Bodyweight work has rep trends; duration/distance-specific charts are not implemented. Best reps may use different weights and best load may use different reps: these summaries are not fixed-load or fixed-rep strength comparisons. Exact-value tables link back to source workouts. Records include eligible estimated 1RM, heaviest weight, best set/session volume, least assistance, most reps and heaviest weight for each exact rep count. Excluded sets do not contribute to trends or records; flagged sets remain inspectable, and correction/exclusion UI is still future work.

The compact logger retains full-width exercise sections, explicit completion, large editable fields and keyboard-aware scrolling. Swipe left to **reveal** Delete, then tap it; the set-number action provides the keyboard/non-gesture alternative. Deleting a set removes it without an alert or undo banner; remaining sets keep their values and order.

Prefilled numbers are targets. Editing clears completion. Finish excludes uncompleted/invalid sets. Historical comparison links expose actual source sets. Chromium touch/viewport tests do not prove comfort on the real phone keyboard; on-device validation is still required.

Weight is normalized to kg and distance to km while retaining source values. Epley estimates apply only to weighted sets of 2–10 reps; a single rep uses recorded load. Assistance/unweighted/duration work does not use resistance estimates. Recorded machine weights are not equated across equipment changes.
