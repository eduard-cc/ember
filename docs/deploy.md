# Shipping, deploy and live checks

Read before merging to `main`, deploying, adding a static asset type, touching the app shell or service worker, or checking the live app.

## Release layout

The live app runs from releases, never from a checkout, so source can be edited and built freely. It runs as the `ember` service account (`docs/operations.md`), so every `~` below is that account's home. The `ember.service` user unit (`ops/systemd/`, installed with `ops/install.sh`) serves `~/.local/share/ember/current`, a symlink to `releases/<commit>/`. A release is one of two kinds:

- An image release (the normal one) holds `IMAGE`, one line naming the image CI published for that code by digest (`ghcr.io/eduard-cc/ember@sha256:<digest>`), `REVISION`, and `dist/`, the web shell copied out of that image. `ember.service` runs it as the `ember-app` container in Ember's own Docker daemon, on the database's Compose network, published on `127.0.0.1` only, read-only, without capabilities, with `--init` and its own limits (768 MiB memory, 1.5 CPUs, 256 tasks) inside `ember-live.slice`.
- A host-built release holds the web shell in `dist/` and the compiled API with its production dependencies in `server/`; `ember.service` runs `server/dist/trial.js` with the account's Node. `ops/deploy.sh --host-build` still makes one, as a fallback while the registry is unavailable.

`ember.service` starts both through `~/.local/lib/ember/start.sh`, a copy of `ops/start.sh` that `ops/install.sh` installs, so advancing the checkout never changes what the unit runs. For an image release it passes the container the variables in `runtime.env` by name, replacing three: the listen address (`0.0.0.0` inside the container), the web root (the image's `/app/web`) and the database URL, whose `127.0.0.1:55438` becomes `ember-postgres:5432` on the Compose network. It refuses an `IMAGE` that is not exactly one image by digest and any other database URL. The daemon never pulls at start: the image is the one `ops/deploy.sh` pulled and checked.

Runtime settings and secrets live in `~/.config/ember/runtime.env` (mode 0600, outside the repository) with `EMBER_WEB_ROOT` set to the absolute path of `~/.local/share/ember/current/dist` (systemd does not expand `~`). The app has its own tailnet device, `ember`, run by the `ember-tailscale.service` user unit (userspace networking, UDP 41642, state in `~/.local/share/ember-tailscale`); its Tailscale Serve config proxies HTTPS 443 to the service on loopback, so the app has its own origin. `EMBER_ORIGIN` must be that address.

## What `ops/deploy.sh` checks

- It deploys the image CI tested and published for the commit's code, never a build of its own. It reads the `ember-image` artifact of the newest green push run of that code (a docs-only commit uses its code commit's run and image) with the account's read-only token and refuses unless the record is exactly one line, `ghcr.io/eduard-cc/ember@sha256:<digest> <commit>`, naming that run's own commit. It pulls that digest (no tag is ever resolved on the host) and refuses unless the image's `org.opencontainers.image.revision` label is that commit and its `source` label is this repository. It copies the web shell out of the image into the release's `dist/`, writes `IMAGE`, switches `current` atomically and restarts the unit.
- Before it switches to an image release it checks that the installed launcher matches the checkout's `ops/start.sh` and that `ember.service` runs it; after a change to either, run `ops/install.sh` in the account first, or every image deploy refuses with "run ops/install.sh".
- `ops/deploy.sh --host-build <commit>` builds `apps/web` and `apps/api` from a `git archive` export instead and keeps only what runs, the host-built layout above. Every other gate is the same.
- After the switch it checks that the serving release owns the port (for a host-built release the unit's own process; for an image release an `ember-app` container running exactly the image `IMAGE` names, published on `127.0.0.1` only, with the listener being the Docker daemon's `rootlesskit` in `ember-docker.service`), `/api/v1/health` on loopback (waiting up to two minutes for startup migrations) and through Serve, and that Serve returns this release's `index.html`, `sw.js`, `manifest.webmanifest` and every precached file byte for byte. Any failure rolls back automatically and alerts the owner.
- A lock prevents overlapping deploys and rollbacks. `ops/auto-deploy.sh` holds it for its whole run and `ops/deploy.sh` reuses it, so a rollback started meanwhile refuses with "another deploy or rollback is running"; run it again once the timer's run ends. The newest five releases in `history` are kept, with the images they name; an image no kept release names is removed from Ember's daemon by its digest (never a prune). Rollback therefore never needs the registry.
- The server applies migrations on startup. It lists a release's migrations with that release's own code (for an image release, the image's Node in a container without network). When a release adds migrations, or is the first image release after a host-built one, the deploy first runs `ops/backup.sh` into `~/.local/share/ember-backups/`, restores it into a validation database, compares record and migration counts with `ember` and drops the copy; any failure cancels the deploy. Writes between the backup and the restart are not in it. The newest three pre-deploy backups are kept; manual archives there are never rotated.
- `ops/test-release-switch.sh` exercises the switch, health check, launcher and rollback across both kinds of release against synthetic releases, a fake `docker` and a throwaway unit; it needs systemd and is local-only. `ops/test-deploy.sh` runs `ops/deploy.sh` and `ops/rollback.sh` against a throwaway git origin, a fake `gh` and `docker` with a synthetic registry and database, and stub backups: every refusal, the backup gate, docs-only commits, automatic rollback, the mixed rollback stack and image retention.

## Shipping through a PR

- Every change reaches `main` through a PR; the `main` ruleset refuses direct pushes, force pushes and deletion, and requires the `CI` check (`docs/ci-and-tests.md`). Work on a short-lived branch, push it and open a PR whose description is one to three plain sentences on what it changes and why.
- Merge with `gh pr merge <n> --squash --auto --match-head-commit <sha>`, where `<sha>` is the head you verified and had reviewed: GitHub squashes once `CI` passes on that exact head (the repository allows auto-merge and squash merges only) and refuses if the branch moved meanwhile. Merging is shipping.
- If `main` moved after the PR's CI ran, merge `origin/main` into the branch (never force-push a pushed branch) and let CI run on the new head.

## Deploying

- Main deploys itself. `ember-auto-deploy.timer` (installed and started by `ops/install.sh`) runs `ops/auto-deploy.sh` five minutes after each run ends. Once CI has passed for the head of `origin/main`, it fast-forwards `~/src/ember` and runs `ops/deploy.sh` on it. While CI is pending or GitHub is unreachable, it waits for the next run. The account reads GitHub with its own read-only token; if that token stops working, every run with a commit to deploy logs "could not read CI results". Once runs have failed to read GitHub for a day, the owner is alerted once; the first run that reads it again resets that (`~/.local/share/ember/github-unreachable` marks when it began).
- A head commit whose CI fails, whose deploy fails, or which `~/src/ember` cannot fast-forward to (not on `main`) is held in `~/.local/share/ember/auto-deploy.hold`: the owner is alerted once and it is never retried. A commit is held while it deploys too, so a run killed by the unit's 30-minute timeout is not retried (systemd's failure alert reports it); `ops/deploy.sh` exits 69 when GitHub or the registry is unreachable or CI is still running, which the timer retries instead. A green run without an image record, a malformed record, an image the registry does not have or with the wrong labels is a failed deploy: held, with one alert. `ops/rollback.sh` holds main's head, so the timer does not put it straight back, however many rollbacks follow. The next commit on main replaces the hold; to retry a held commit, run `ops/deploy.sh <commit>` by hand as the service account (`docs/operations.md`). A failed health check alerts twice: once from the rollback, once from the hold.
- Merging is shipping: a merged PR is live within about five minutes after `main`'s push CI passes, plus the image pull. Still check the live app after each change ships.
- `ops/test-auto-deploy.sh` checks those decisions, and the alert route, against a throwaway git origin, a fake `gh`, `hermes` and `curl` and a stub deploy; it is local-only.
- `ops/deploy.sh <commit>` sources `ops/lib.sh` from the checkout it is run from (the service account's `~/src/ember`); the release it builds with `git archive` never updates those scripts. Fast-forward that checkout first (`git fetch && git merge --ff-only origin/main`, keeping untracked files), or the deploy runs an old health check.
- Never build, install or run dev servers in either `~/src/ember`: the service account's must stay a clean `main` for `ops/deploy.sh`, and the owner's is the base for worktrees.
- The deploy refuses commits not on `origin/main` or whose latest code commit has no successful push CI run (a docs-only commit inherits its code ancestor's run without waiting for its own; cancelled runs don't count).
- A release that adds migrations is preceded by `ops/backup.sh` plus `ops/restore-check.sh`, and a count comparison against `ember`. Migrations are never rolled back, and a release lacking migrations the database already has is refused.
- Undo with `ops/rollback.sh` (previous healthy release from `~/.local/share/ember/history`, either kind; the image is still local, so it needs no network). Run it as the service account: `sudo /usr/local/sbin/ember-run -- bash -c 'cd ~/src/ember && ops/rollback.sh'`. Roll forward again with `ops/deploy.sh <commit>`, which reuses the kept release.
- To pause deploys, stop the timer in the account (`ember-run -- systemctl --user stop ember-auto-deploy.timer`) and start it again afterwards; `ops/install.sh` starts it too. For a short manual step, hold the deploy lock on file descriptor 9, as `ops/auto-deploy.sh` does: `ember-run -- bash -c 'exec 9>~/.local/share/ember/deploy.lock && flock -n 9 && cd ~/src/ember && <commands>'`. The timer waits meanwhile, and `ops/deploy.sh` and `ops/rollback.sh` run inside it reuse the lock.

## Live app

- The live origin is `EMBER_ORIGIN` in `~/.config/ember/runtime.env`. It is served by Ember's own tailnet device (`ember-tailscale.service`), so it does not appear in the host's plain `tailscale serve status`.
- Verify a deploy by comparing live `/sw.js` with `~/.local/share/ember/releases/<sha>/dist/sw.js`. For an image release, also check that `ember-app` runs the digest in `releases/<sha>/IMAGE` (`ops/docker.sh inspect --format '{{.Image}}' ember-app` against `ops/docker.sh image inspect --format '{{.Id}}' <image>`). The app's own log stays in `journalctl --user -u ember.service`.
- The server gzips responses only for clients that send `Accept-Encoding` (never Range requests). The plain-`curl` health check sends none, so its byte-for-byte comparisons still see the uncompressed files.
- Small images are inlined into the JS bundle by Vite, so a live check must compare hashes of non-inlined assets rather than grep for file names.

## Static assets and the precache

The production server sends only files allowed by `apps/api/src/static-files.ts` (`index.html`, `sw.js`, the public shell files, and `assets/*.{js,css,woff2,webp}`). `apps/web/scripts/pwa-build.ts` imports the same rule and fails the build if the service worker would precache a file the server refuses, and `ops/deploy.sh`'s health check fetches `sw.js`, the manifest and every precached URL through Serve byte for byte, rolling back and naming the file on a mismatch. A single missing file makes the service worker's `cache.addAll` fail, leaving installed apps on the old shell while the API looks healthy. A new asset type means widening that one rule. After deploys that touch the shell, still check that the service worker activates on a phone.

## Read-only live offline-shell check

Use a fresh Pixel 6 browser context and intercept only `**/api/**` with a synthetic unavailable response, so owner history and mutations stay off the wire. Avoid a catch-all `context.route('**/*')`, even with `route.continue()`: in Chrome it left the reloaded page without a service-worker controller. Wait for activation, reload under the worker, then test offline reload and reopening in a fresh tab. Never print private page text.
